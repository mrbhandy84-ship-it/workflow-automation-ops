# Circuit Breaker

The circuit breaker pattern prevents cascading failures when a downstream dependency becomes unavailable or degraded. The breaker sits in the call path and tracks failure rates over a rolling window. When the failure rate crosses a threshold, the breaker opens — rejecting further calls immediately without attempting the downstream request. After a cooldown period, it moves to a half-open state that allows a limited number of probe requests through. Sustained success closes the breaker; any failure during half-open returns it to open.

The implementation tradeoff that matters most in practice is how the breaker interacts with the job retry system. A circuit breaker that opens mid-queue will cause retries to exhaust against the open breaker rather than actually reaching the downstream service. The correct configuration holds retried jobs at the queue level — increasing visibility timeout and backoff — rather than burning attempts against an open circuit. This requires the breaker state to be observable by the retry policy layer, not just by the call site.

Per-dependency breaker configuration is worth the operational overhead. A global breaker that trips on any downstream failure is too coarse — it causes unnecessary degradation when only one of several dependencies is impaired. Granular breakers, keyed by service or endpoint class, allow the rest of the workflow to continue while the affected path recovers. Shared breaker state across worker instances should be stored centrally (Redis is the common choice) rather than maintained per-process, or breaker state will diverge under load.
